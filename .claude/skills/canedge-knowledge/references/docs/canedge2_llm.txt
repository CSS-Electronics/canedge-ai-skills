# Introduction

The CANedge2 enables stand-alone logging of CAN bus and LIN bus data to an SD-card.

The device offers a range of configuration options including message filtering, prescaling, transmit messages, cyclic logging, compression, encryption, message routing and more.

Further, the CANedge2 can be accessed remotely (log, configuration and firmware files) through a local/remote S3 server (push) or a web server (poll) running on the device.

The CANedge is based on open standards: no proprietary tools required, no subscription models and no vendor lock-in. Users can leverage the CANedge tools, or integrate with custom applications.

It is recommended to visit the **CANedge2 introduction page** on the CSS Electronics website (csselectronics.com).

# Glossary

The terms below are explained as they apply to the CANedge.

<a id="term-5-V-power-output"></a>

5 V power output
: A switchable 5 V output on the [CH2](#term-CH2) connector for powering external devices.

<a id="term-Access-point"></a>

Access point
: A network device, such as a router, that WiFi devices connect to.

<a id="term-Acknowledge"></a>

Acknowledge
: The confirmation of a correctly received CAN frame, sent by the receiving nodes in the acknowledge slot of the frame.

<a id="term-Bit-rate"></a>

Bit rate
: The speed of a CAN bus or LIN bus in bits per second. Classical CAN uses one bit rate for the whole frame. [CAN FD](#term-CAN-FD) uses a [nominal bit rate](#term-Nominal-bit-rate) and a [data bit rate](#term-Data-bit-rate).

<a id="term-Bit-timing"></a>

Bit timing
: The [CAN channel](#term-CAN-channel) settings that define the [bit rate](#term-Bit-rate) and the [sample point](#term-Sample-point).

<a id="term-Bucket"></a>

Bucket
: A container for [objects](#term-Object) on an [S3 server](#term-S3-server), similar to a file folder.

<a id="term-Bus-load"></a>

Bus load
: The percentage of time the bus is not idle. 100 percent means the bus is never idle.

<a id="term-Bus-off"></a>

Bus-off
: A CAN node state entered after too many errors. The node no longer takes part in the bus traffic.

<a id="term-Byte-order"></a>

Byte order
: The order of the bytes of a value spanning several bytes. *Intel* byte order is little-endian (least significant byte first). *Motorola* byte order is big-endian (most significant byte first).

<a id="term-CAN-bus"></a>

CAN bus
: A physical CAN bus network. The device can be connected to one CAN bus per [CAN channel](#term-CAN-channel).

<a id="term-CAN-channel"></a>

CAN channel

<a id="term-CAN-1"></a>

CAN-1

<a id="term-CAN-2"></a>

CAN-2
: One of the two physical CAN interfaces of the device. Each CAN channel can be connected to one [CAN bus](#term-CAN-bus).

<a id="term-CAN-FD"></a>

CAN FD
: CAN with flexible data rate. An extension of CAN with up to 64 data bytes per frame and an optional higher [data bit rate](#term-Data-bit-rate).

<a id="term-CAN-internal"></a>

CAN-internal
: A virtual CAN channel carrying the [internal signals](#term-Internal-signals) generated by the device.

<a id="term-Certificate-bundle"></a>

Certificate bundle
: A single file holding several certificates, such as the certificates trusted for [TLS](#term-TLS) connections.

<a id="term-CH1"></a>

CH1

<a id="term-CH2"></a>

CH2
: The two DB9 connectors of the device. Each connector carries one [CAN channel](#term-CAN-channel) and one [LIN channel](#term-LIN-channel).

<a id="term-Checksum-type"></a>

Checksum type
: The method used to calculate the checksum of a LIN frame. The *classic* checksum covers the data bytes only. The *enhanced* checksum also covers the protected ID.

<a id="term-Configuration-file"></a>

Configuration file
: The JSON file on the SD-card that configures the device.

<a id="term-Control-signal"></a>

Control signal
: A [signal](#term-Signal) in a received message used to start or stop the reception (logging) and/or transmission of messages.

<a id="term-Cyclic-logging"></a>

Cyclic logging
: A logging mode in which the oldest [log files](#term-Log-file) are deleted to make room for new ones when the SD-card is full.

<a id="term-Data-bit-rate"></a>

Data bit rate
: The [bit rate](#term-Bit-rate) used for the data phase of [CAN FD](#term-CAN-FD) frames with bit rate switching.

<a id="term-DBC"></a>

DBC
: A CAN database file format describing how [signals](#term-Signal) are encoded in messages.

<a id="term-Default-configuration"></a>

Default configuration
: The [configuration file](#term-Configuration-file) with the default settings of a [firmware version](#term-Firmware-version).

<a id="term-Device"></a>

Device
: The CANedge2 CAN bus and LIN bus data logger described by this manual.

<a id="term-Device-file"></a>

Device file
: The JSON file (`device.json`) on the SD-card with information about the device.

<a id="term-Device-ID"></a>

Device ID
: A globally unique 8-digit hexadecimal identifier of a device.

<a id="term-Endpoint"></a>

Endpoint
: The address of a server, such as the [S3 server](#term-S3-server).

<a id="term-Epoch-time"></a>

Epoch time
: Time as the number of seconds since 1970-01-01 00:00:00 UTC.

<a id="term-Error-frame"></a>

Error frame
: A CAN bus or LIN bus error event.

<a id="term-Extended-ID"></a>

Extended ID
: A 29-bit CAN message ID (see [ID-format](#term-ID-format)).

<a id="term-Filter"></a>

Filter
: A rule applied to received messages, accepting or rejecting them based on their ID.

<a id="term-Firmware-file"></a>

Firmware file
: The file (`firmware.bin`) used to update the device firmware.

<a id="term-Firmware-package"></a>

Firmware package
: The firmware download (`firmware-XX.YY.ZZ.zip`). It contains the [firmware file](#term-Firmware-file) and the matching [default configuration](#term-Default-configuration), [schema file](#term-Schema-file) and [UI schema file](#term-UI-schema-file).

<a id="term-Firmware-version"></a>

Firmware version
: The version of the device firmware, in the format `MAJOR.MINOR.PATCH`.

<a id="term-Frame-table"></a>

Frame table
: A table defining the data length and [checksum type](#term-Checksum-type) of LIN message IDs.

<a id="term-Hardware-version"></a>

Hardware version
: The version of the device hardware.

<a id="term-Heartbeat"></a>

Heartbeat
: Either the [CAN-internal](#term-CAN-internal) message periodically reporting the device status, or the periodic upload of the [device file](#term-Device-file) to the [S3 server](#term-S3-server).

<a id="term-ID-format"></a>

ID-format
: The format of a CAN message ID: *Standard* (11-bit) or *Extended* (29-bit).

<a id="term-Internal-signals"></a>

Internal signals
: [Signals](#term-Signal) generated by the device itself, such as the device status. They are carried by [CAN-internal](#term-CAN-internal).

<a id="term-J1939"></a>

J1939
: A higher-layer protocol on CAN, used in heavy-duty vehicles. It uses [extended IDs](#term-Extended-ID) that contain the priority, the [PGN](#term-PGN) and the source address.

<a id="term-LIN-bus"></a>

LIN bus
: A physical LIN bus network, consisting of one [master](#term-Master) and one or more [slaves](#term-Slave). The device can be connected to one LIN bus per [LIN channel](#term-LIN-channel).

<a id="term-LIN-channel"></a>

LIN channel

<a id="term-LIN-1"></a>

LIN-1

<a id="term-LIN-2"></a>

LIN-2
: One of the two physical LIN interfaces of the device. Each LIN channel can be connected to one [LIN bus](#term-LIN-bus).

<a id="term-Log-file"></a>

Log file
: A file holding the logged data in [MDF4](#term-MDF4) format.

<a id="term-Master"></a>

Master
: The LIN node that schedules the messages on a [LIN bus](#term-LIN-bus) and transmits the message headers.

<a id="term-MDF4"></a>

MDF4
: ASAM MDF version 4. An industry-standard binary file format for measurement data.

<a id="term-Module-firmware"></a>

Module firmware
: The firmware running on a module integrated in the device, separate from the device firmware.

<a id="term-Monitoring-mode"></a>

Monitoring mode
: A CAN mode in which a node only receives. It neither [acknowledges](#term-Acknowledge) nor transmits, so it does not affect the bus.

<a id="term-Nominal-bit-rate"></a>

Nominal bit rate
: The [bit rate](#term-Bit-rate) used for all of a frame except the data phase of [CAN FD](#term-CAN-FD) frames with bit rate switching.

<a id="term-Normal-mode"></a>

Normal mode
: A CAN mode in which a node receives, [acknowledges](#term-Acknowledge) and transmits.

<a id="term-NTP"></a>

NTP
: Network Time Protocol. A protocol for synchronizing clocks with a time server.

<a id="term-Object"></a>

Object
: A file stored on an [S3 server](#term-S3-server), with some added metadata.

<a id="term-OTA"></a>

OTA

<a id="term-COTA"></a>

COTA

<a id="term-FOTA"></a>

FOTA
: Over-the-air update. A remote update of the device, such as of the configuration (COTA) or the firmware (FOTA).

<a id="term-PGN"></a>

PGN
: Parameter group number. The part of a [J1939](#term-J1939) message ID that identifies the content of the message.

<a id="term-Power-cycle"></a>

Power cycle
: Switching the device off and on again by removing and restoring power.

<a id="term-Power-safe"></a>

Power safe
: Able to lose power at any time without corrupting data.

<a id="term-Prescaling"></a>

Prescaling
: Reducing the number of messages with the same ID accepted by a [filter](#term-Filter), based on a count, a time or a change of the data.

<a id="term-Publisher"></a>

Publisher
: The LIN node that provides the data (response) of a message. Each message has one publisher, either the [master](#term-Master) or a [slave](#term-Slave).

<a id="term-Remote-frame"></a>

Remote frame
: A CAN frame requesting data from another node. It carries no data itself. Also called *RTR frame*.

<a id="term-Restricted-mode"></a>

Restricted mode
: A CAN mode in which a node receives and [acknowledges](#term-Acknowledge), but does not transmit.

<a id="term-Routing"></a>

Routing
: Forwarding of received messages from one channel to another, optionally with a different ID.

<a id="term-RTC"></a>

RTC
: Real-time clock. A battery-backed clock that keeps the date and time while the device is unpowered.

<a id="term-S3"></a>

S3
: An object storage interface developed by Amazon Web Services and supported by many servers.

<a id="term-S3-server"></a>

S3 server
: A server implementing the [S3](#term-S3) interface, such as a cloud service or a self-hosted server.

<a id="term-Sample-point"></a>

Sample point
: The position in percent within a bit at which the bus level is read. Defined through the [bit timing](#term-Bit-timing).

<a id="term-Schema-file"></a>

Schema file
: The JSON file on the SD-card that defines the rules of the [configuration file](#term-Configuration-file), such as the allowed fields and values.

<a id="term-Session"></a>

Session
: The [log files](#term-Log-file) recorded from one boot of the device, stored in a directory of their own.

<a id="term-Signal"></a>

Signal
: A value encoded in a range of bits of the message data. Defined by its bit position, bit length, [byte order](#term-Byte-order), factor and offset, as in [DBC](#term-DBC) files.

<a id="term-Silent-mode"></a>

Silent mode
: A CAN mode in which a node does not transmit messages: [restricted mode](#term-Restricted-mode) or [monitoring mode](#term-Monitoring-mode).

<a id="term-Slave"></a>

Slave
: A LIN node that responds to the message headers transmitted by the [master](#term-Master).

<a id="term-Split"></a>

Split
: One [log file](#term-Log-file) of a [session](#term-Session). The logged data is split into several log files by file size or time.

<a id="term-Standard-ID"></a>

Standard ID
: An 11-bit CAN message ID (see [ID-format](#term-ID-format)).

<a id="term-Subscriber"></a>

Subscriber
: A LIN node that receives the data of a message provided by its [publisher](#term-Publisher).

<a id="term-Timestamp"></a>

Timestamp
: The time of a logged record, such as a received message.

<a id="term-TLS"></a>

TLS
: Transport Layer Security. A protocol that encrypts network communication and authenticates the server using certificates.

<a id="term-UI-schema-file"></a>

UI schema file
: The JSON file on the SD-card that describes how configuration editors present the [configuration file](#term-Configuration-file).

<a id="term-Web-server"></a>

Web server
: A server running on the device, providing access to the files on the SD-card through WiFi.

## Logging

* Storage
  > * Extractable industrial-grade micro SD-card (8-32 GB)
  > * Standard FAT filesystem (can be read directly by a PC)
  > * Logging to the industry-standard ASAM MDF4 file format (`.MF4`)
* Organization
  > * Log files grouped by session (one per boot)
  > * Log files split based on configurable file size or time
  > * Optional cyclic logging mode (oldest log file is deleted when the SD-card is full)
* Performance
  > * Simultaneous logging from 2 x CAN bus + 2 x LIN bus
  > * Message timestamping with 50 µs resolution
  > * High message rate
  > * Optional data compression (LZSS)
* Security and integrity
  > * Globally unique device ID with customizable device name
  > * Power safe (device can be disconnected during operation without risk of data corruption)
  > * Optional end-to-end data encryption (AES-128-GCM)

## Real-time clock (RTC)

* High-precision real-time clock retains date and time when device is off
* The real-time clock can be automatically synced from various sources<sup>[1](#fn-rtc-sync)</sup>

## CAN bus (x2)

* Physical
  > * Two physical CAN bus interfaces
  > * Industry-standard DB9 connectors
* Transceiver
  > * Compliant with ISO 11898-2 (high-speed CAN)
  > * Ideal passive behavior when unpowered (high impedance / no load)
  > * Short-circuit protection
  > * Transient protection
  > * TXD dominant timeout (prevents network blocking in the event of a failure)
  > * Data rates up to 5 Mbit/s<sup>[2](#fn-can-bit-rates-fd)</sup>
* Controller
  > * Based on MCAN IP from Bosch
  > * Compliant with CAN Protocol Version 2.0 Part A, B and ISO 11898-1
  > * Compliant with ISO CAN FD and Bosch CAN FD
  > * Bit rate: *Auto-detect* (from list<sup>[3](#fn-can-bit-rates-auto)</sup>), *Bit rate (simple)* (from list<sup>[4](#fn-can-bit-rates-manual)</sup>) or *Bit timing (advanced)*
  > * 128 standard CAN ID + 64 extended CAN ID filters (per interface)
  > * Advanced filter configuration: Range, mask, acceptance, rejection
  > * Configurable transmit messages, single-shot or periodic (up to 224 messages<sup>[5](#fn-can-transmit-list)</sup>)
  > * Message prescaling based on:
  >   > * Count
  >   > * Time
  >   > * Change in data
  > * Support for remote frames (RTR)
  > * Silent modes: *Restricted* (receive and acknowledge) or *Monitoring* (receive only)
  > * Supports all CAN-based protocols (J1939, CANopen, OBD2, NMEA 2000, …)<sup>[6](#fn-can-protocol)</sup>
* Application
  > * Cross-channel *control signal* for start/stop of reception/transmission

---

## LIN bus (x2)

* Physical
  > * Two physical LIN bus interfaces
  > * Industry-standard DB9 connectors
  > * No internal diode and resistor for master mode
* Transceiver
  > * Protection: ±8 kV HBM ESD, ±1.5 kV CDM, ±58 V bus fault
  > * Supports 4 V to 24 V applications
  > * TXD dominant timeout (prevents network blocking in the event of a failure)
  > * Data rates up to 20 kbit/s
* Controller
  > * Support for both master and slave modes
  > * Can be the publisher or a subscriber of each message
  > * Automatic<sup>[7](#fn-lin-automatic)</sup> and custom data lengths
  > * Classic and Enhanced checksum formats
  > * Configurable transmit messages, single-shot or periodic

## Supply quality

The supply voltage shall be kept within the specified range (see [Electrical](https://canlogger.csselectronics.com/canedge-docs/ce2/specification/index.html.md#electrical)) at all times. The device is internally
protected against low-energy voltage events which can be expected as a result of supply wire
noise, ESD and stub-wire inductance.

If the supply line is shared with inductive loads, care should be taken to ensure high-energy voltage events do not reach the device. Automotive environments often include several sources of electrical hazards, such as load dumps (disconnection of battery while charging), relay contacts, solenoids, alternators, fuel injectors, etc. The internal protection circuitry of the device is not capable of handling high-energy voltage events directly from such sources.

---

## CAN bus physical requirements (ISO 11898-2)

ISO 11898-2 defines the basic physical requirements of a high-speed CAN bus network. Some of
these are listed below:

* Max line length (determined by bit rate)
* Line termination (120 Ω line termination at each end of data line)
* Twisted data lines
* Ground offsets in range -2 V to +7 V

---

## Grounding

ISO 11898-2 tolerates some level of ground offset between nodes. To ensure the offset remains
within range, it is recommended to use a single-point ground reference for all nodes connected to the CAN bus. This may require the ground wire to be carried along with data wires.

If a secondary CAN bus network is connected to CH2, care must be taken to ensure that the ground potentials of the two networks can safely be connected through the common ground in the device.

---

## Cable shielding

Shielding is not needed in all applications. If shielding is used, it is recommended that a short pigtail be crimped to the shield end at each connector.

---

## CAN bus stub length

It is recommended that the CAN bus stub length is kept short. The stub length is defined as the length from the *main* data line wires to the connection point of the CAN bus nodes.

### Security

Some configuration field values can be encrypted to hide sensitive data stored in the configuration file (passwords etc.). This section provides a technical summary and resource suggestions for implementing the encryption.

A field value must be encrypted as described below when the field definition that applies to it is marked with `"x-encrypted": true` in the schema file (e.g. when the key format is set to *Encrypted*).

The field encryption feature uses a key agreement scheme based on Elliptic Curve Cryptography (ECC) (similar to the one used in a TLS handshake). The scheme allows the device and user to compute the same shared secret, without exposing any secrets. The shared secret is in turn used to generate a symmetric key, which is used to encrypt / decrypt protected field values.

The following sequence diagram illustrates the process of encrypting configuration fields:

```mermaid
sequenceDiagram
    participant Device (device.json)
    participant Config as Device (config-XX.YY.json)
    participant User
    Device (device.json)->>User: 1. Load device public key (base64)

    User->>User: 2. Decode (base64) device public key
    User->>User: 3. Generate user ECC key pair
    User->>User: 4. Calculate shared secret
    User->>User: 5. Derive symmetric key from shared secret

    User->>User: 6. Encode (base64) user public key
    User->>Config: 7. Set user public key in config

    loop 8. Set values
        User->>Config: 8a. Encrypt field value
        User->>Config: 8b. Concatenate iv and ct
        User->>Config: 8c. Encode (base64)
        User->>Config: 8d. Set value in config
    end
```

The steps are:

1. Load device public key field (`kpub`) from the `device.json` file
2. Decode the device public key (base64). The decoded key is 64 bytes: the X and Y coordinates (32 bytes each, big-endian), without a prefix byte
3. Generate random user key pair (public and private) using curve `secp256r1`
4. Calculate shared secret using device public key and user private key. The shared secret is the X coordinate of the resulting point (32 bytes, big-endian)
5. Derive shared symmetric key using HMAC-SHA256 with the ASCII string `config` as data and the shared secret as key. Use the first 16 bytes of the output.
6. Encode user public key in the same format as the device public key (X and Y coordinates, 64 bytes, base64). The device uses it to calculate the same shared symmetric key for decryption
7. Set the encoded user public key in the device configuration file (`kpub`)
8. Use AES-128 CTR to encrypt protected fields using the symmetric key. Use a random 16-byte initialization vector as the initial counter block. The resulting initialization vector (iv) and cipher text (ct) are concatenated (iv + ct), encoded as standard base64 with `=` padding and stored in the configuration file

#### NOTE
All protected fields must be encrypted with the symmetric key derived from the user public key set in `kpub`.

#### NOTE
By storing the symmetric key, it is possible to change specific protected fields - without updating the user public key (and in turn all other protected fields).

#### NOTE
Keep the field order of the default configuration. The device reads the configuration file in one pass, so the user public key (`kpub`) and the key format of a field must come before the encrypted value.

#### Encryption tools

Tools are provided with the CANedge which can be used to encrypt sensitive fields.

#### Example Python code

Passwords can be batch-encrypted across multiple devices using e.g. Python. The following basic code sample illustrates how Python can be used to encrypt plain-text data. The example code requires Python 3 and the `pycryptodome` crypto library:

[`Python example code`](https://canlogger.csselectronics.com/canedge-docs/ce2/_downloads/ed9aaf674d893f0ce9e1cee99af5feff/canEdgeSecurity.py)

## Configuration explained

*This section contains additional information and examples.*

### File split

File splitting can be based on file size or file size and time:

* `split_time_period = 0`: Split based on size only
* `split_time_period > 0`: Split based on both size and time, whichever is reached first

Time-based splits are aligned to midnight (00:00:00 UTC). With `split_time_period` set to `3600`, a new file is started at every full hour (01:00, 02:00, …). The `split_time_offset` shifts the split times, e.g. with `split_time_offset` set to `600`, new files are started at 00:10, 01:10, 02:10, … The offset must be less than the split time period.

The first file of a session is started at boot. The following files are started at the aligned split times, e.g. when the device boots at 01:37 with a split time period of `3600`, the first file covers 01:37 to 02:00.

#### NOTE
If multiple devices upload log files to the same server, use different `split_time_offset` values to spread the uploads over time, instead of all devices uploading at the same time.

#### Limits

The filesystem limits should be considered when configuring the split size and time:

* SD-card size
* Max `1024` sessions
* Max `256` splits (log files) in each session. When the limit is reached, a new session is started.

The above limits result in a maximum of `1024*256=262144` log files if fully utilized.

If the session count limit is reached, the device will either:

* Stop logging if cyclic logging is disabled<sup>[1](#fn-offload-log-files)</sup>
* Delete the oldest session if cyclic logging is enabled

If the SD-card becomes full (no more space), the device will either:

* Stop logging if cyclic logging is disabled<sup>[1](#fn-offload-log-files)</sup>
* Delete the oldest split file from the oldest session if cyclic logging is enabled

### Compression

Log files can be compressed on the device during logging using a variant of the LZSS algorithm based on [heatshrink](https://github.com/atomicobject/heatshrink). Compressed files have `.MFC` as file extension (or `.MFM` if also encrypted). A larger window size improves the compression ratio, but may cause message loss on very busy networks.

The table below lists results for J1939 and OBD2 data with different window size configurations<sup>[3](#fn-comptable)</sup>:

|   Window size (bytes) | J1939 % (range)   | OBD2 % (range)   |
|-----------------------|-------------------|------------------|
|                   256 | 49.7 (47.1-51.4)  | 32.0 (30.3-32.8) |
|                   512 | 49.5 (46.3-51.6)  | 30.2 (29.6-31.1) |
|                  1024 | 41.4 (38.9-45.5)  | 30.0 (29.6-30.8) |

Decompression can be done using an implementation of LZSS (see [Compressed files](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/log-file.html.md#compressed-files) for the file format) or using the tools provided with the CANedge.

#### NOTE
The split size set in `split_size` considers the size of the compressed data. I.e. if the split size is 10 MB, the resulting file sizes become 10 MB regardless of whether compression is used or not.

---

### Encryption

Log files can be stored as encrypted (AES-GCM) `.MFE` files. The encryption password can be stored in encrypted form in the configuration file (see [Security](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/general.html.md#security)).

#### NOTE
It is recommended to use a 40+ character password for proper encryption.

Decryption can be done using an implementation of AES-GCM, with the key derived from the password using PBKDF2-HMAC-SHA256 (salt and iteration count stored in the file header, see [Encrypted files](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/log-file.html.md#encrypted-files) for the file format), or using the tools provided with the CANedge.

---

### Error frames

Enabling error frames will log errors across all interfaces, both CAN and LIN. This can decrease the performance of the device due to the added logging load.

For more information on the logged errors, see [CAN errors](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/index.html.md#can-errors) and [LIN errors](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/index.html.md#lin-errors).

## Configuration explained

*This section contains additional information and examples.*

The CANedge uses a real-time clock (RTC) with battery backup, which allows it to retain the absolute date & time when the device is not powered. The RTC enables the CANedge to add absolute timestamps to recorded messages.

The time zone and a time offset can be set with the `timezone` and `adjustment` fields.

---

### Synchronization methods (`sync`)

The RTC time can be *retained*, *manually set*, *synchronized via CAN bus* or *synchronized via network*.

Times received from an external synchronization source are sanity checked before they are applied.

#### NOTE
When using an external synchronization source, the [TimeExternal signals](https://canlogger.csselectronics.com/canedge-docs/ce2/signals/index.html.md#timeexternal-signals) can be used to confirm that the device correctly receives and understands the time synchronization information. To log the `TimeExternal` messages, a CAN-internal filter accepting the *TimeExternal* message (ID `0x5`) must be enabled.

#### Manual update

Manually changing the RTC is *only needed* if the RTC time has been completely reset (e.g. after a battery replacement). The following sequence explains how the RTC can be manually set:

1. Select the *Manual update* `sync` method and set the current UTC time in `manual_date_time` (for the format, see [Configuration file fields](#configuration-file-fields))
2. Power on the device and wait a few seconds to allow the device to read the manually set time
3. Power off the device
4. Change the `sync` method to *Retain current time*
5. Power on the device again
6. Verify that the new absolute time is now correctly retained across power cycles
7. Set the time zone (`timezone`) and the adjustment (`adjustment`) if needed

#### NOTE
The internally stored *session counter* is lost when the battery is removed. See [Setting session counter](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/index.html.md#setting-session-counter) for information on how to set the session counter.

#### CAN bus

The RTC can be synchronized based on a CAN bus message. The interpretation of message data signals is configurable.

Time information can be provided via either physical CAN bus channel.

The synchronization method depends on the time difference between the RTC time and the external time provided via CAN bus:

- Time difference exceeds `tolerance`: The RTC time is directly set to the external time (discrete jump in time)
- Time difference within `tolerance`: The RTC time slowly tracks the external time (continuous time)<sup>[1](#fn-time-tracking)</sup>

The synchronization message data is assumed to include the external time and optionally a *valid* flag indicating if the external time should be applied or not:

- *Valid signal* (can be disabled, see Example 2): 1: Time signal is valid, else: Time signal is invalid
- *Time signal* (mandatory): The current UTC time as *Epoch* (floating-point number of seconds since 1970-01-01 00:00:00 UTC)

#### WARNING
Avoid using a high-frequency CAN bus message for time synchronization. If the frequency of the time message is high, consider using a time prescaler in the filter (see [Message prescaling](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/filter.html.md#message-prescaling)) to reduce the frequency to e.g. one message per minute.

The configuration of the signals uses a concept similar to that used by  *.DBC* files. In case a  *.DBC* file is available (describing the interpretation of the synchronization message), the information from the file can be used directly for configuration. For more information, see [Signal interpretation](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/signal.html.md#signal-interpretation).

Example 1: Using both the *valid* signal and *time* signal (time message generated by a *CANmod.GPS* device).

- The valid signal is 1 bit starting at index 0. The factor and offset are chosen such that the decoded signal becomes *1* when the time signal is valid.
- The time signal is 40 bits starting at index 8. After applying *factor* and *offset*, the result becomes Epoch in seconds.

| Signal   | Type     | Byte order   |   Bit position |   Bit length |   Factor |     Offset |
|----------|----------|--------------|----------------|--------------|----------|------------|
| Valid    | Unsigned | Intel        |              0 |            1 |    1     |          0 |
| Time     | Unsigned | Intel        |              8 |           40 |    0.001 | 1577840400 |

Example 2: Same as Example 1 but without using the *valid* signal.

- The valid signal length is set to 0. With a factor of 0 and offset of 1, the result always becomes 1 (valid).

| Signal   | Type     | Byte order   |   Bit position |   Bit length |   Factor |     Offset |
|----------|----------|--------------|----------------|--------------|----------|------------|
| Valid    | Unsigned | Intel        |              0 |            0 |    0     |          1 |
| Time     | Unsigned | Intel        |              8 |           40 |    0.001 | 1577840400 |

#### Network

The RTC can be synchronized using the WiFi connection and an external time (NTP) server. When enabled, the device periodically requests the current time from the time server.

#### WARNING
Make sure firewalls etc. allow NTP (port 123) traffic.

#### WARNING
Community-driven NTP pools can occasionally return an incorrect time.

Examples of some publicly available time servers:

- `*.pool.ntp.org` (pool with wildcard)
- `0.pool.ntp.org` (specific pool)
- `europe.pool.ntp.org`
- `north-america.pool.ntp.org`
- `time.windows.com`
- `time.google.com`

#### NOTE
The device supports NTP server hostnames only (not IP addresses).

The difference between the RTC time and the network time is compared to the configured `tolerance`. For more information on the tolerance, see the [synchronization via CAN bus section](#can-bus).

---

### Adjustment (`adjustment`)

The adjustment is a fixed offset in seconds added to the timestamps.

---

### Time zone (`timezone`)

The configured time zone is only used in MDF4 log file headers. MDF4 readers supporting localization can optionally apply the time zone when parsing log files.

* <a id='fn-time-tracking'>**[1]**</a> Continuous tracking requires that an updated external time is available at least once each hour.

## Configuration explained

*This section contains additional information and examples.*

The 5 V power output on CH2 can be used to power external devices (see [5 V power output](https://canlogger.csselectronics.com/canedge-docs/ce2/hardware/connector.html.md#v-power-output)). It is configured in the `secondaryport` section of the configuration file.

The output is controlled by a daily power schedule, defined as a list of power-on intervals (`from` / `to`):

* No intervals: The output is always off
* One interval with both `from` and `to` set to `00:00`: The output is always on

#### NOTE
Power scheduling has a resolution of 1 min and 1 min tolerance.

#### NOTE
Power scheduling always uses UTC time (regardless of the configured time zone).

Example: The 5 V power output is scheduled to be on daily in the intervals `00:00-04:00` and `12:00-16:00`. Configuration:

```text
"secondaryport": {
  "power_schedule": [
    {
      "from": "00:00",
      "to": "04:00"
    },
    {
      "from": "12:00",
      "to": "16:00"
    }
  ]
}
```

The power is turned off when the time changes from 03:59 to 04:00 and from 15:59 to 16:00.

## CAN errors

The CANedge can detect and log errors on the CAN bus if enabled in the [logging configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/log.html.md#error-frames). The detected errors are categorized as follows:

* Bit-stuffing errors
* Form errors
* CRC errors
* Bit errors
* Acknowledge errors

Logged CAN errors contain no information about the ID, flags or data of the affected frame.

In the *Restricted* and *Monitoring* [modes](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/phy.html.md#mode), the CANedge does not signal errors on the bus.

The CANedge recovers from the bus-off state automatically.

*This section contains additional information and examples.*

### Mode

The `mode` field configures to what extent the CANedge is allowed to communicate on the CAN bus.

#### NOTE
It is recommended to use the most restrictive mode possible.

---

### Retransmission

The `retransmission` field configures how the CANedge should react when message transmissions fail. Failed transmissions can either be aborted or retried.

---

### Bit rate configuration mode

The `bit_rate_cfg_mode` field selects how the bit rate is configured. With *Auto-detect*, the CANedge attempts to determine the bit rate automatically (see below). If the bit rate is known, it can be set with *Bit rate (simple)*. For more advanced cases, use *Bit timing (advanced)*.

---

### Bit rate / bit timing

The input clock to the CAN bus controllers is 40 MHz.

The bit rate mode *Bit rate (simple)* supports the following list of bit rates<sup>[1](#fn-sp)</sup><sup>[2](#fn-ssp)</sup>:

| Bit rate    |   BRP |   Quanta |   SEG1 |   SEG2 |   SJW |
|-------------|-------|----------|--------|--------|-------|
| **5K**      |   100 |       80 |     63 |     16 |     4 |
| **10K**     |    50 |       80 |     63 |     16 |     4 |
| **20K**     |    25 |       80 |     63 |     16 |     4 |
| **33.333K** |    10 |      120 |     95 |     24 |     4 |
| **47.619K** |     8 |      105 |     83 |     21 |     4 |
| **50K**     |    10 |       80 |     63 |     16 |     4 |
| **83.333K** |     4 |      120 |     95 |     24 |     4 |
| **95.238K** |     4 |      105 |     83 |     21 |     4 |
| **100K**    |     5 |       80 |     63 |     16 |     4 |
| **125K**    |     4 |       80 |     63 |     16 |     4 |
| **250K**    |     2 |       80 |     63 |     16 |     4 |
| **500K**    |     1 |       80 |     63 |     16 |     4 |
| **800K**    |     1 |       50 |     39 |     10 |     4 |
| **1M**      |     1 |       40 |     31 |      8 |     4 |
| **2M**      |     1 |       20 |     15 |      4 |     4 |
| **4M**      |     1 |       10 |      7 |      2 |     2 |

In *Auto-detect* mode, the CANedge attempts to determine the bit rate from the bit rates in the table above (up to 1M). Depending on factors such as data patterns, bit rate deviation etc., it may not always be possible to detect the bit rate automatically.

#### NOTE
It is recommended to set the bit rate manually when possible.

#### WARNING
Bit rate auto-detect cannot be used to detect a CAN FD switched bit rate. Use *Bit rate (simple)* for CAN FD networks with bit rate switching.

In *Bit timing (advanced)* mode, the bit timing is set directly: BRP (bit rate prescaler) divides the input clock into time quanta, SEG1 and SEG2 (time segments 1 and 2) set the number of quanta before and after the sample point (in addition to a fixed synchronization segment of 1 quantum at the start of the bit), and SJW (synchronization jump width) sets the maximum number of quanta by which a bit can be adjusted to resynchronize. See the [bit timing list](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/bit_timing.html.md#bit-timing) for valid bit timing configurations.

---

### Examples

Example: Converting bit timing settings from a device with a different input clock frequency (`CLK`).

Settings to match (based on an 80 MHz input clock):

- Bit rate: 2M
- BRP: 1
- Quanta: 40
- SEG1: 29
- SEG2: 10
- Sample point: 75%

The above settings are based on an input clock with frequency:

$$
CLK = BR \cdot Q \cdot BRP = 2000000 \cdot 40 \cdot 1 = 80\text{ MHz}
$$

The CANedge uses a 40 MHz input clock. To obtain a bit rate of 2M with a 40 MHz input clock, the number of quanta is calculated as:

$$
Q = \frac{CLK/BRP}{BR} = \frac{40000000/1}{2000000} = 20
$$

To obtain a sample point of 75%, SEG1 is calculated as:

$$
SEG_1 = \frac{SP \cdot Q}{100} - 1 = \frac{75 \cdot 20}{100} - 1 = 14
$$

Now, SEG2 is calculated as:

$$
SEG_2 = Q - SEG_1 - 1 = 20 - 14 - 1 = 5
$$

SJW must not be larger than SEG2. Here, the largest value allowed by the schema is used.

The equivalent bit timing settings using the 40 MHz input clock of the CANedge become:

- BRP: 1
- SEG1: 14
- SEG2: 5
- SJW: 4

---
* <a id='fn-sp'>**[1]**</a> All bit rates in the table use a sample point (SP) of 80%.
* <a id='fn-ssp'>**[2]**</a> The CAN FD secondary sample point (SSP) is set to the same as the CAN FD sample point (SP).

### Filter processing

The filter elements in the list of filters are processed sequentially starting from the first element. Processing stops on the first filter match or when the end of the filter list is reached.

Example: A message matches filter element 3. Filter element 4 is not evaluated.

```mermaid
graph LR

B[Filter element 2]
C[Filter element 3 - match]
D[Filter element 4 - not evaluated]
A-->B
B-->C
C-->D

style C fill:#62c74e
style D fill:#adadad
```

**Messages matching no filters are rejected.**

#### NOTE
The default configuration file contains filters accepting all standard and extended ID messages on CAN-1 and CAN-2 (remote frames are rejected by default, see `remote_frames`).

---

### Filter name

Filters can be assigned an optional `name`. The name is not used when processing a filter.

---

### Filter state

The `state` of filter elements can be *Enable* or *Disable*. Disabled filter elements are ignored, as if they are not in the list of filters. If there are no enabled filters in the list, then all messages are rejected.

By disabling a filter element (instead of deleting the element) it can be easily enabled at a later time.

---

### Filter types

The filter `type` can be either *Acceptance* or *Rejection*:

* If a message matches an *Acceptance* filter it is accepted
* If a message matches a *Rejection* filter it is rejected
* If a message does not match a filter, the next filter in the list is processed

The filter list can hold a combination of *Acceptance* and *Rejection* filter elements. The first matching filter element determines if a message is accepted or rejected. *Acceptance* and *Rejection* filters can be combined to generate a complex message filtering mechanism.

Example: A message matches acceptance filter 3. Rejection filter 4 is not evaluated. The message is accepted.

### Filter method

Both *Acceptance* and *Rejection* filters can be defined by range or mask (`method`).

---

#### Filter range method

With the *Range* method, the filter defines a range of IDs which are compared to the message ID. Message IDs within the range (both start and end included) match the filter.

The fields *F1* and *F2* respectively define the start (from) and the end (to) of the range.

Example: Standard ID filter with range from $100_{16}$ to $\text{1FF}_{16}$. The filter is set up with:

* *F1* (from): `100`
* *F2* (to): `1FF`

| ID-format   | ID (hex)   | Match   |
|-------------|------------|---------|
| Standard    | 0FF        | No      |
| Standard    | 100        | Yes     |
| Standard    | 1FF        | Yes     |
| Standard    | 200        | No      |
| Extended    | 100        | No      |

---

#### Filter mask method

With the *Mask* method, the filter defines an ID and a mask which are compared to the message ID.

The fields *F1* and *F2* respectively define the *Filter-ID* and the *Filter-mask*.

A message matches a mask filter if the following condition is true<sup>[1](#fn-mask)</sup>:

```text
(filter_id & filter_mask) == (message_id & filter_mask)
```

Below are some practical examples of filters using the *mask* method.

Example: Filter configuration which accepts one specific message ID: $\text{7D0}_{16} = 11111010000_2$. The filter ID is set to the value of the message ID to accept. The filter mask is set to all ones, such that all bits of the filter are considered, as given in (1).

$$
\begin{array}{cc}
    \begin{array}{cc}
        \begin{array}{l}
        \text{Filter ID}\\
        \text{Filter mask}\\
        \text{Masked filter}
        \end{array}
        &
        \begin{array}{r}
        11111010000_2\\
        \&\color{green}{11111111111_2}
        \\\hline
        11111010000_2
        \end{array}
    \end{array}
    (1)
    &
    \begin{array}{cc}
        \begin{array}{l}
        \text{Message ID}\\
        \text{Filter mask}\\
        \text{Masked ID}
        \end{array}
        &
        \begin{array}{r}
        11111010000_2\\
        \&\color{green}{11111111111_2}
        \\\hline
        11111010000_2
        \end{array}
    \end{array}
    (2)
\end{array}
$$

To test if the message passes the filter, the filter mask is applied to the message ID as given in (2). The masked filter and the masked ID are equal, so the message matches the filter.

The filter is set up with:

* *F1* (filter ID): `7D0`
* *F2* (filter mask): `7FF`

Example: Filter configuration which accepts two message IDs:

* $\text{7D0}_{16} = 11111010000_2$
* $\text{7D1}_{16} = 11111010001_2$

Note that the two binary numbers are identical except for the rightmost bit. To design a filter which accepts both IDs, the mask field can be used to *mask out* the rightmost bit - such that it is not considered when the filter is applied. In (1) the mask is set such that the rightmost bit is not considered (shown in red).

$$
\begin{array}{cc}

\text{Filter mask}\\
\text{Masked filter}
\end{array}

\\\hline

\end{array}
\end{array}
(1)
&
\begin{array}{cc}
\begin{array}{l}
\text{Message ID}\\
\text{Filter mask}\\
\text{Masked ID}
\end{array}

$$

To test if the messages pass the filter, the mask is applied to the message ID $11111010001_2$ as given in (2). The masked filter and the masked ID are equal, so the message matches the filter.
Note that both $11111010000_2$ and $11111010001_2$ match the filter, as the rightmost bit is not considered by the filter (the rightmost bit is masked out).

The filter is set up with:

* *F1* (filter ID): `7D0`
* *F2* (filter mask): $11111111110_2 = \text{7FE}_{16}$ (`7FE`)

Example: J1939 - filter configuration which accepts PGN 61444 (EEC1) messages.

J1939 message frames use 29-bit message IDs. The Parameter Group Number (PGN) is defined by 18 of the 29 bits. The remaining 11 bits define the priority and source address of the message. It is often useful to configure a filter to accept a specific PGN while ignoring the remaining 11 bits - this can be done using the filter mask.

Below, the left red bits represent the 3-bit priority, the green bits the 18-bit PGN and the right red bits the 8-bit source address of the 29-bit message ID.

$$
\color{red}{000}\color{green}{111111111111111111}\color{red}{00000000}_{2} = \text{3FFFF00}_{16}

$$

Message ID bits in positions with zero bits in the filter mask are ignored. By using $\text{3FFFF00}_{16}$ as filter mask, the priority and source address are ignored.

To specifically accept PGN $\text{F004}_{16}$ messages, the filter ID is set to $\text{F00400}_{16}$ - note that the final 8 bits ($\text{00}_{16}$) represent the source address which is ignored by the filter mask (these bits can be any value).

The filter uses the *Extended* ID-format and is set up with:

* *F1* (filter ID): `F00400`
* *F2* (filter mask): `3FFFF00`

Filter mask $\text{3FFFF00}_{16}$ can be used for all J1939 PGN (PDU2) messages. To accept specific PGNs, the filter ID is adjusted. To accept one specific PGN (as in the example above), the filter ID is set to the specific PGN with $\text{00}_{16}$ appended to represent the ignored source address field.

#### NOTE
For PDU1 messages (PGNs with a PDU format below $\text{F0}_{16}$), the lower 8 bits of the PGN hold the destination address. Filter mask $\text{3FFFF00}_{16}$ then only accepts messages for one specific destination address. To accept the PGN for all destination addresses, use filter mask $\text{3FF0000}_{16}$.

### Message prescaling

Message prescaling can be used to reduce the number of received messages for a given message ID. Prescaling is applied to the messages accepted by the associated filter. Prescaling can only be configured for acceptance filters. The list of filters can be assigned a mixture of prescaler types.

Applying prescaling can dramatically reduce log file size, allowing longer logging on the SD-card and reducing upload time and data usage.

The prescaling type can be set to:

* *None*: Disables prescaling
* *Count*: Prescales based on message occurrences
* *Time*: Prescales based on message period time
* *Data*: Prescales based on changes in the message data payload

The first message with a given ID is always accepted regardless of prescaling type.

#### NOTE
A maximum of 100 unique message IDs can be prescaled for each physical CAN bus channel (15 for CAN-internal). These are the first unique IDs accepted by a filter with prescaling enabled. Messages with additional unique IDs are accepted without prescaling.

---

#### Count

Count prescaling reduces the number of messages with a specific ID by a constant factor (prescaling value). A prescaling value of 2 accepts every 2nd message (with a specific ID), a value of 3 every 3rd and so on<sup>[2](#fn-countbyone)</sup>.

Example: Count prescaling applied to ID $100_{16}$ with a prescaling value of 3.

| ID (hex)   |   ID occurrences | Result   |
|------------|------------------|----------|
| $100_{16}$ |                1 | Accept   |
| $100_{16}$ |                2 | Reject   |
| $100_{16}$ |                3 | Reject   |
| $100_{16}$ |                4 | Accept   |
| $100_{16}$ |                5 | Reject   |

#### Time

Time prescaling sets a lower limit on the time interval (period time) of a specific message ID. This is done by rejecting messages until at least the prescaler time has elapsed<sup>[3](#fn-timeresample)</sup>. The prescaler timer is reset each time a message is accepted. The prescaling value is set in milliseconds<sup>[4](#fn-timesubmilli)</sup>.

This prescaler type is e.g. useful if a slowly changing signal (low frequency signal content) is broadcast on the CAN bus at a higher rate than needed to represent the signal.

Example: A slowly changing temperature measurement broadcast every 10 ms (100 Hz). Prescaled to a minimum time interval of 100 ms (prescaling value set to 100).

![Plot of a sinusoidal signal over 2 s. The 10 ms samples before prescaling are shown as crosses, the samples kept after time prescaling (one every 100 ms) as circles. The kept samples still follow the signal shape.](configuration/can/prescaling_time.png)

Example: Time prescaling applied to ID $200_{16}$ with a time interval of 1000 ms.

| ID (hex)   | Message timestamp [ms]   | Prescaler timer [ms]   | Result   |
|------------|--------------------------|------------------------|----------|
| $200_{16}$ | **200**                  | 0                      | Accept   |
| $200_{16}$ | 700                      | 500                    | Reject   |
| $200_{16}$ | 1000                     | 800                    | Reject   |
| $200_{16}$ | **1200**                 | 1000 -> 0 (reset)      | Accept   |
| $200_{16}$ | 1300                     | 100                    | Reject   |
| $200_{16}$ | **3200**                 | 2000 -> 0 (reset)      | Accept   |
| $200_{16}$ | **4200**                 | 1000 -> 0 (reset)      | Accept   |
| $200_{16}$ | **5200**                 | 1000 -> 0 (reset)      | Accept   |

---

#### Data

Data prescaling can be used to only accept messages when the data payload changes. A mask can be set to only consider changes in one or more specific data bytes. The mask works on a byte level: each bit of the mask corresponds to one data byte, with the rightmost (least significant) bit representing the first data byte. The mask is entered in hex and can cover all 64 data bytes of a CAN FD frame.

Examples of data masks:

* `""`: An empty mask triggers on any data change (equivalent to mask value `FFFFFFFFFFFFFFFF`)
* `1`: Triggers on changes to the first data byte (D0) (binary `1`)
* `2`: Triggers on changes to the second data byte (D1) (binary `10`)
* `3`: Triggers on changes to the first or second data byte (D0 or D1) (binary `11`)
* `9`: Triggers on changes to the first or fourth data byte (D0 or D3) (binary `1001`)
* `FF`: Triggers on changes to any of the first 8 data bytes (binary `11111111`)
* `100`: Triggers on changes to the ninth data byte (D8) (binary `100000000`)

If the data payload contains more data bytes than entered in the mask, then changes to the additional bytes are ignored by the prescaler.

#### WARNING
Data prescaling assumes that the payload length of a specific message ID is constant.

Example: A discretely changing signal is broadcast every 100 ms (10 Hz). A data prescaler is used such that only changes in the signal are logged.

![Plot of a step signal over 2 s with values between 0 and 3. The 100 ms samples before prescaling are shown as crosses, the samples kept after data prescaling as circles. Only the first sample and the samples where the value changes are kept.](configuration/can/prescaling_data.png)

| $300_{16}$ | 00     | 11     |   22 | 33     | Reject   |
| $300_{16}$ | 00     | **BB** |   22 | 33     | Accept   |
| $300_{16}$ | **AA** | BB     |   22 | 33     | Accept   |
| $300_{16}$ | AA     | BB     |   22 | **DD** | Accept   |
| $300_{16}$ | AA     | BB     |   22 | DD     | Reject   |

Example: Data prescaling applied to ID $300_{16}$ with mask `1` (considering only changes to the first data byte). D0-D3 form a 4-byte payload (with D0 the first data byte).

| ID (hex)   | D0     | D1     |   D2 | D3     | Result   |
|------------|--------|--------|------|--------|----------|
| $300_{16}$ | 00     | 11     |   22 | 33     | Accept   |
| $300_{16}$ | 00     | 11     |   22 | 33     | Reject   |
| $300_{16}$ | 00     | **BB** |   22 | 33     | Reject   |
| $300_{16}$ | **AA** | BB     |   22 | 33     | Accept   |
| $300_{16}$ | AA     | BB     |   22 | **DD** | Reject   |
| $300_{16}$ | AA     | BB     |   22 | DD     | Reject   |

### Period and delay

Transmit messages can be configured as either *single-shot* or *periodic*.

The `period` value determines if a message is single-shot (0) or periodic (>0). The interpretation of the `delay` value depends on whether the message is single-shot or periodic (see more below).

#### NOTE
When possible, it is recommended to spread the transmit messages over time using `delay` offsets to reduce peak bus load.

---

#### Single-shot

A transmit message is *single-shot* when the `period` is set to 0. In this case, the `delay` is the time between boot<sup>[3](#fn-single-shot-delay)</sup> and the single-shot transmission. Delaying a single-shot message can be useful if e.g. the receiving node has a long boot time.

Example: Four *single-shot* transmit messages are configured with different `delay` values.

| Message   |   Period [ms] |   Delay [ms] |
|-----------|---------------|--------------|
| A         |             0 |            0 |
| B         |             0 |           20 |
| C         |             0 |           40 |
| D         |             0 |           60 |

The table below illustrates the transmission scheduling (crosses mark transmissions).

| t [ms]   | 0   | 10   | 20   | 30   | 40   | 50   | 60   | 70   | 80   |
|----------|-----|------|------|------|------|------|------|------|------|
| A        | ✕   |      |      |      |      |      |      |      |      |
| B        |     |      | ✕    |      |      |      |      |      |      |
| C        |     |      |      |      | ✕    |      |      |      |      |
| D        |     |      |      |      |      |      | ✕    |      |      |

#### NOTE
The transmissions do not coincide.

---

#### Periodic

A transmit message is *periodic* when the `period` value is more than zero. In this case, the `delay` is the time from the start of each period to the transmission (the *offset* within the period). Consequently, the `delay` value **must be less than** the `period` value.

Example: Four periodic transmit messages are configured with `delay` values set to zero.

| Message   |   Period [ms] |   Delay [ms] |
|-----------|---------------|--------------|
| A         |            10 |            0 |
| B         |            20 |            0 |
| C         |            30 |            0 |
| D         |            40 |            0 |

The table below illustrates the transmission scheduling (crosses mark transmissions).

| t [ms]   | 0   | 10   | 20   | 30   | 40   | 50   | 60   | 70   | 80   |
|----------|-----|------|------|------|------|------|------|------|------|
| A        | ✕   | ✕    | ✕    | ✕    | ✕    | ✕    | ✕    | ✕    | ✕    |
| B        | ✕   |      | ✕    |      | ✕    |      | ✕    |      | ✕    |
| C        | ✕   |      |      | ✕    |      |      | ✕    |      |      |
| D        | ✕   |      |      |      | ✕    |      |      |      | ✕    |

Example: Four periodic transmit messages are configured with the same `period` value and different `delay` values.

## Configuration explained

*This section contains additional information and examples.*

The control signal can be used to control message reception (i.e. logging) and/or message transmission (e.g. processing of the transmit list) for each CAN bus channel. The control signal has a flexible configuration allowing for integration with many protocols. The control signal can e.g. be used to start / stop logging based on some application parameters, such as speed, RPM, time-of-day or discrete events.

#### NOTE
The control signals can trigger on [Internal signals](https://canlogger.csselectronics.com/canedge-docs/ce2/signals/index.html.md#internal-signals) such as [TimeCalendar](https://canlogger.csselectronics.com/canedge-docs/ce2/signals/index.html.md#timecalendar-signals) (e.g. log only from 08:00 to 16:00).

Signals are configured the same way as in DBC files. If a DBC file is available (describing the interpretation of the control message signals), the information from the file can be used directly for configuration. For more information, see [Signal interpretation](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/signal.html.md#signal-interpretation).

Control signal overview:

* A control signal can be configured for each CAN bus channel
* A control signal can be based on messages from any channel
* One message (ID and ID mask) is used for start and one for stop. These can be different or the same
* The message payload is decoded on the device, making it easy to set start / stop ranges

The message ID is matched using `id` and `id_mask`, in the same way as a filter using the *Mask* method (see [Filter mask method](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/filter.html.md#filter-mask-method)). A mask of all ones (e.g. `7FF`) matches one specific ID.

The start and stop ranges include the low and high values and are evaluated as follows:

* If the start / stop ranges do not overlap, they are evaluated individually
* If the start range lies within the stop range, then start takes precedence (see examples below)
* If the stop range lies within the start range, then stop takes precedence (see examples below)

#### NOTE
The control signal does not cause log file splits.

#### NOTE
The control signal only uses messages accepted by the [filter and prescaler](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/filter.html.md#filter) of the channel on which they are received.

#### NOTE
The initial states of message reception and transmission are set in configuration section [CAN general](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/general.html.md#can-general).

### Examples

Example: Start / stop ranges not overlapping (start above stop).

This can, for example, be used to start logging when a speed signal exceeds 7500 and stop when it drops below 2500.

Start trigger:

* High: 10000
* Low:  7500

Stop trigger:

* High: 2500
* Low:  0

![Plot of the control signal on CH1 (sine between 0 and 10000) with the start range 7500-10000 and the stop range 0-2500. Markers show that CH2 is logged from when the signal enters the start range until it enters the stop range.](configuration/can/control_signal_plots/high.png)

Example: Start / stop ranges not overlapping (start below stop).

This can, for example, be used to start logging when a pressure signal drops below 2500 and stop when it rises above 7500 again.

Start trigger:

* High: 2500
* Low:  0

Stop trigger:

* High: 10000
* Low:  7500

![Plot of the control signal on CH1 (sine between 0 and 10000) with the start range 0-2500 and the stop range 7500-10000. Markers show that CH2 is logged from when the signal enters the start range until it enters the stop range.](configuration/can/control_signal_plots/low.png)

Example: Start range lies within stop range, start takes precedence.

This can, for example, be used to start logging when a temperature signal lies within the range 2500 to 7500 and stop when it is outside this range.

Start trigger:

* High: 7500
* Low:  2500

Stop trigger:

* High: 10000
* Low:  0

![Plot of the control signal on CH1 (sine between 0 and 10000) with the start range 2500-7500 inside the stop range 0-10000. Markers show that CH2 is logged only while the signal is between 2500 and 7500.](configuration/can/control_signal_plots/mid_start.png)

* Low:  -5000

* High: 2500
* Low:  -2500

# LIN

This page documents the *LIN* configuration.

The configurations of LIN-1 and LIN-2 (`lin_1` and `lin_2`) are identical. On the following pages, `lin` refers to either of them.

The LIN configuration is split into the following sections:

* [Overview](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/index.html.md)
* [LIN physical](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/phy.html.md)
* [Frame table](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/frame_table.html.md)
* [LIN transmit](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/transmit.html.md)

---

## Topology

A LIN bus consists of a *master* node and one or more *slave* nodes. The *master* schedules the messages on the LIN bus by transmitting the message headers (with the message ID). The *slave* nodes react to the headers.

The data of a message (the response) is provided by one node, the *publisher* of the message. The other nodes receiving the data are *subscribers* of the message. The *master* can be the publisher of some messages and a *subscriber* of others.

The configuration of the LIN network shall ensure that each message has exactly one publisher.

An example of the bus topology with the CANedge connected as a *slave* is illustrated below:

```mermaid
graph TD
p[Master]
s1[Slave 1]
s2[Slave N]
ce[CANedge]
b1["#0160;"]
style b1 width:0px

p---b1
s1---b1
s2---b1
ce---b1
```

LIN bus with one master, N slaves and the CANedge

The CANedge is primarily intended to act as a *slave* on the LIN bus. If no *master* node is present, the CANedge can emulate a simple *master* node by setting `mode` to *Master* in the [physical configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/phy.html.md#lin-physical). In this case, the scheduling of messages on the network has to be done through the [transmit configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/transmit.html.md#lin-transmit) for the interface. Since only static data can be entered in the configuration, the simple *master* node emulation cannot perform dynamic operations based on the LIN bus activity. The master termination must be added externally (see [LIN data](https://canlogger.csselectronics.com/canedge-docs/ce2/hardware/connector.html.md#lin-data)).

---

## Data length

Unless configured otherwise, the device assumes that the length of the LIN frame data payload is always defined by the message ID (bits 4 and 5 of the identifier), as defined in the table below:

| Message ID            |   Data length (bytes) |
|-----------------------|-----------------------|
| 00-31 (`0x00`-`0x1F`) |                     2 |
| 32-47 (`0x20`-`0x2F`) |                     4 |
| 48-63 (`0x30`-`0x3F`) |                     8 |

This can be overridden in the [frame table](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/frame_table.html.md#frame-table).

---

## Checksum

The CANedge supports LIN 1.3 *classic* checksum and LIN 2.0 *enhanced* checksum formats. By default, all frames use the enhanced checksum, except the diagnostic frames ID `0x3C` and `0x3D`, which use the classic checksum. This can be overridden on a frame-by-frame basis in the [frame table](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/frame_table.html.md#frame-table).

---

## LIN errors

The CANedge can detect and log errors on the LIN bus if enabled in the [logging configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/log.html.md#error-frames). The detected errors are categorized as follows:

* Checksum errors
* Receive errors
* Synchronization errors
* Transmission errors

The amount of associated data depends on the type of error. For example, synchronization errors contain no message ID, as they occur before the ID is transmitted. Only checksum errors include checksum information.

### Checksum errors

Checksum errors denote that the node has calculated a different checksum than the one embedded in the LIN message on the bus. This can indicate an incorrect length or checksum type for the frame ID in the CANedge frame table.

Example: In case no information is known about the LIN bus in advance, the default frame table can be used with error logging enabled to help reverse-engineer the actual frame table. Any message IDs deviating from the default frame table (and present on the LIN bus) are logged as errors. These IDs can then be reconfigured in the CANedge frame table, in an attempt to find the correct settings.

Note that it can be necessary to change both message length and checksum type in order to get a valid configuration.

### Receive errors

Receive errors are logged when a fixed part of the LIN message is not as expected, or when the node detects a mismatch between the value being transmitted and the value sensed on the LIN bus.

### Synchronization errors

Synchronization errors indicate an invalid synchronization field in the start of the LIN message, or that the bit rate detected from the synchronization field deviates too much from the configured bit rate.

### Transmission errors

Transmission errors are logged when a message header is not answered, i.e. no node on the LIN bus provides the response (data) for the message ID.

## Configuration explained

*This section contains additional information and examples.*

The interpretation of the *transmit list* depends on the `mode` field of the [physical configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/lin/phy.html.md#configuration-file-fields):

### Master mode

In *Master* mode, the CANedge transmits the message headers scheduled by `period` and `delay`.

The number of bytes entered in the `data` field determines who provides the response (data) of the message:

* Length of `data` is above zero: The CANedge is the publisher of the message and provides the data.
* Length of `data` is zero: A slave node is expected to be the publisher of the message and to provide the data (satisfying the *frame table*).

#### NOTE
*LDF* (LIN Description File) files define the scheduling as a schedule table: a list of frames, each with a slot time, transmitted one after the other in a repeating cycle. To map a schedule table to the transmit list, set `period` of each frame to the cycle time of the table (the sum of all slot times), and `delay` to the start time of the frame’s slot within the cycle.

### Slave mode

In *Slave* mode, the CANedge is the publisher of the messages in the transmit list: it provides the data when the master transmits a header with a matching ID. The number of bytes provided shall satisfy the *frame table*.

#### WARNING
IDs must be unique. If the transmit list contains multiple frames using the same ID, then only the first entry is used.

# Routing

This page documents the *routing* configuration.

#### WARNING
When routing messages between channels, care should be taken to avoid message ID collisions on the destination channel.

#### NOTE
It is recommended to keep the frequency of the messages matching each routing rule to a maximum of 50 Hz (a minimum period of 20 ms), e.g. by utilizing filter prescalers.

> ##### On this page
> 
> * [Configuration file fields](#configuration-file-fields)
> * [Configuration explained](#configuration-explained)
> * [Examples](#examples)

The CANedge supports configurable routing of messages from CAN-internal (see [internally generated signals](https://canlogger.csselectronics.com/canedge-docs/ce2/signals/index.html.md#internal-signals)), CAN-1, CAN-2, LIN-1, and LIN-2 to CAN-1 and/or CAN-2. E.g. the CAN-internal [Heartbeat](https://canlogger.csselectronics.com/canedge-docs/ce2/signals/index.html.md#heartbeat-signals) message can be routed to a physical CAN bus channel to provide device status.

#### Routing of messages to CAN-1 (left) and CAN-2 (right)

| ```mermaid<br/>flowchart LR<br/>SRC1["CAN-internal, CAN-2, LIN-1, LIN-2"] -.-> CAN-1<br/>```   | ```mermaid<br/>flowchart LR<br/>SRC2["CAN-internal, CAN-1, LIN-1, LIN-2"] -.-> CAN-2<br/>```   |
|------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------|

When the CANedge receives a message on CAN-internal, CAN-1, CAN-2, LIN-1, or LIN-2, it is compared to each (enabled) entry in the routing list. If a match is found, the message is *routed* to the configured destination channel<sup>[1](#fn-destination-configurable)</sup>.

#### NOTE
A message can trigger multiple routing rules (e.g. be routed to multiple destination channels).

#### NOTE
A message is only routed if the source channel is allowed to receive and the destination channel is allowed to transmit.

#### NOTE
For CAN source channels, only messages accepted by the [filter and prescaler](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/can/filter.html.md#filter) of the source channel are routed.

See routing [examples](#examples) for practical use cases.

## Configuration explained

*This section contains additional information and examples.*

Below, the routing rule fields are explained in detail.

---

### Name

The `name` field is optional and is not used when processing a rule.

---

### State

The `state` field defines if a routing rule is active. Disabled rules are ignored, as if they are not in the list of rules. By disabling a rule (instead of deleting it), it can be easily enabled at a later time.

---

### Log

The `log` field defines if routed messages are included in the log file. When enabled, a routed message is logged once it has been successfully transmitted on the destination bus (transmission acknowledged).

When `log` is enabled, a rule only routes a new message once the previous routed message has been transmitted. Messages matching the rule in the meantime are not routed, which can reduce the number of routed messages on busy buses.

#### NOTE
The *received* message on the source channel (routed to the destination channel) is logged regardless of the value of this field.

---

### Source channel

The `chn_src` field defines the routing rule source channel. The source channel can be either virtual (see [internally generated signals](https://canlogger.csselectronics.com/canedge-docs/ce2/signals/index.html.md#internal-signals)) or physical.

---

### Source ID-format

The `id_format_src` field defines the ID-format of the source message (on the source channel).

---

### Source ID (hex)

The `id_src` field defines the ID-value of the source message (on the source channel).

---

### Destination channel

The `chn_dst` field defines the routing rule destination channel. The destination channel can be either of the physical CAN bus channels.

#### NOTE
The routing rule is ignored if the source and destination channels are the same.

---

### Destination ID-format

The `id_format_dst` field defines the ID-format of the destination message (on the destination channel).

---

### Destination ID (hex)

The `id_dst` field defines the ID-value of the destination message (on the destination channel).

---

### Scan mode (`mode`)

The device supports active and passive scan modes to find available access points.

#### Active mode

The device actively transmits a probe request on each channel when searching for APs. Active scan is the fastest way to find and connect to an AP.

#### Passive mode

The device passively listens for beacons on each channel. Passive scan is silent, but it takes additional time to find and connect to an AP.

Access points with a hidden SSID (not broadcast) can only be found in active mode.

---

### Multiple WiFi access points (`accesspoint`)

The CANedge2 supports multiple access points. The device periodically scans for WiFi access points. If known SSIDs are found, the device tries to connect to them one at a time, in the order of the `accesspoint` list. If the connection fails or the signal strength is below `minrssi`, the device tries the next known SSID found.

A `minrssi` of 0% (default) means that the device attempts to connect to the AP, even if the signal strength is practically non-existent.

The access point passwords can be stored in encrypted form in the configuration file (see [Security](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/general.html.md#security)).

#### NOTE
During a WiFi password migration, multiple identical SSIDs with different passwords can be entered in the configuration file. The device tries each entry in list order until one succeeds.

### Request style (`request_style`)

S3 supports two different request styles: *path-style* and *virtual-hosted-style*. The device supports both styles.

With the virtual-hosted-style, the subdomain is specific to the bucket, which makes it possible to use DNS to map a specific bucket to an IP address.

#### WARNING
Some S3 servers may only support one of the two request styles.

Path-style HTTP request header example:

```none
GET /[BUCKET_NAME]/[OBJECT_NAME] HTTP/1.1
Host: [DOMAIN]
...
```

Virtual-hosted-style HTTP request header example:

```none
GET /[OBJECT_NAME] HTTP/1.1
Host: [BUCKET_NAME].[DOMAIN]
...
```

[S3 summary]:

# S3 summary

S3 is an object storage concept developed by Amazon Web Services (AWS). Objects<sup>[1](#fn-object)</sup> are organized into buckets<sup>[2](#fn-bucket)</sup>. S3 is designed to be scalable, secure, reliable, fast and interoperable. S3 is a modern alternative to FTP, suitable for systems with many nodes/clients.

S3 is managed through the publicly documented S3 REST (HTTP) API, a de facto standard for object storage. The S3 REST API has been adopted by several open-source projects, allowing for free self-hosted object (file) storage solutions. Additionally, the S3 REST API is now also supported by competing cloud services.

S3 SDKs are available for all major programming languages, making it easy to manage S3 servers from custom applications.

In short, the S3 REST API can be used to communicate with object storage servers provided by any S3-compatible cloud service or any S3-compatible self-hosted server solution (e.g. MinIO). This makes S3 ideal for systems ranging from a few devices with storage hosted on a regular PC to thousands of devices with storage hosted in the cloud.

---
* <a id='fn-object'>**[1]**</a> *Objects* are similar to files, with some added metadata.
* <a id='fn-bucket'>**[2]**</a> *Buckets* are similar to file folders.

#### NOTE

## TLS certificates

TLS typically uses a chain of certificates to establish trust. At the top of the chain is the root certificate authority (CA). In the example below, the root certificate is used to sign (approve) a *server* certificate.

```mermaid
graph TD
subgraph root["Root"]
    root_key["Private key"]
    root_cert["Public cert"]
end
subgraph server["Server"]
    server_key["Private key"]
    server_cert["Public cert"]
end
root_key -- "Signs" --> server_cert
server_cert -- "References" --> root_cert
```

Certificate chain. The root private key signs the server public certificate, which references the root public certificate.

When the CANedge connects to the server using TLS, the server sends its public certificate, and the CANedge decides whether to trust it.

Installing the root (public) certificate on the CANedge instructs it to trust any certificate signed by that root.

#### NOTE
When using a hostname as an endpoint (e.g. `s3.eu-north-1.amazonaws.com`), the CANedge verifies that the hostname matches the certificate Common Name (CN) or is included in the list of *SANs* (Subject Alternative Names). If no match is found, the connection is refused.

#### NOTE
The CANedge adds the endpoint hostname to the TLS `SNI` (Server Name Indication) extension field.

---

## Installing certificates

The CANedge supports up to 10 trusted certificates as a bundled PKCS#7 (`.p7b`) file.

#### WARNING
The installed certificates must all have distinct *Subjects* (the certificate `Subject` field).

The following describes how to prepare and install trusted certificates on the CANedge.

---

### Prepare certificate(s)

Trusted certificates are stored in a single file (`certs_server.p7b`). The flowchart below shows how to prepare the certificate bundle depending on the number of certificates to install:

```mermaid
graph TD
    A(Acquire certificates) --> B[Number of certificates]
    B -->|Zero | D[Clear]
    B -->|One | E[Rename]
    B -->|Multiple | F[Bundle]
    G(Install on device)
    D --> G
    E --> G
    F --> G
```

#### Zero certificates (Clear)

Clear all loaded certificates by creating an empty/blank file called `certs_server.p7b`.

#### One certificate (Rename)

Prepare a single certificate by renaming:

1. Acquire the trusted certificate (e.g. the root certificate) in a supported format (`.pem`, `.cer`, `.crt`, `.der`)
2. Rename the certificate to `certs_server.p7b`

#### Multiple certificates (Bundle)

Prepare multiple certificates by creating a PKCS#7 bundle containing all the certificates.

Generation of certificate bundles requires a tool, such as the free [OpenSSL](https://openssl-library.org/) toolkit<sup>[1](#fn-openssl)</sup>. Using OpenSSL, multiple certificates can be included in a bundle following the steps below:

1. Acquire the trusted certificates (e.g. root certificates) in a supported format<sup>[2](#fn-opensslbundle)</sup>
2. Copy all the certificates into a single directory (e.g. `cert1.pem`, `cert2.pem`, … `certN.pem`)
3. Open a console/command prompt in the directory storing the certificates, and run the following OpenSSL command (example with two certificates):

```console
$ openssl crl2pkcs7 -nocrl -certfile cert1.pem -certfile cert2.pem -out certs_server.p7b
```

---

### Local installation of certificate(s)

The certificate bundle (`certs_server.p7b`) is installed by placing it in the root of the SD-card.

---

### Remote installation of certificate(s)

The certificate bundle (`certs_server.p7b`) is installed by placing it on the S3 server. For more information, refer to [Server certificates over-the-air](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/s3/s3_management.html.md#server-certificates-over-the-air).

---

### List of installed certificates

Installed certificates can be verified by inspecting the `device.json` file (written to the SD-card and uploaded to S3).
The `certs_server_sha1` field contains a list of hashes of successfully loaded certificates.

A certificate hash is computed by running the *SHA-1* algorithm over the values of the certificate *subject* field (ordered as in the certificate binary).

Example: Compute certificate hash of certificate `DigiCertGlobalRootCA.crt`.

1. List certificate *subject* value fields using `openssl`:

```console
$ openssl x509 -noout -subject -in DigiCertGlobalRootCA.crt
subject=C = US, O = DigiCert Inc, OU = www.digicert.com, CN = DigiCert Global Root CA
```

1. Compute *SHA-1* over concatenated subject values:

$$
\texttt{SHA1}(\texttt{"USDigiCert Incwww.digicert.comDigiCert Global Root CA"}) = \\ \texttt{"0A0DEFC689D4ECD558C0A95C524E1146F5C3D789"}

$$

---
* <a id='fn-openssl'>**[1]**</a> Linux: the package manager of the distribution. macOS: [Homebrew](https://brew.sh/). Windows: included in [Git for Windows](https://git-scm.com/downloads/win).
* <a id='fn-opensslbundle'>**[2]**</a> The input certificate format must be PEM/base64-encoded DER.

## Buckets

Each CANedge device is associated with a specific S3 *bucket* name<sup>[1](#fn-s3-bucket-share)</sup>. Depending on the configuration, the device uploads files to, and checks for configuration updates in, that bucket.

#### NOTE
The device is not able to create a bucket. Buckets must be created on the server before the device is connected.

---

## Device ID

Each CANedge device carries a globally unique 4-byte device ID (e.g. `AABBCCDD`). The device ID is used in the communication with S3 so that multiple devices connected to the same bucket do not conflict. The root path of a given device is given by the bucket name and the unique ID:

`[BUCKET_NAME]/[DEVICE_ID]`

---

## Log files

The device uploads closed log files to the S3 server. When a log file has been successfully uploaded, it is deleted from the SD-card. Log files pushed to the server use the same path structure as on the SD-card (see [Naming](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/log-file.html.md#naming)), with the `LOG` directory replaced by the bucket name and the upload time added to the file name:

`[BUCKET_NAME]/[DEVICE_ID]/[SESSION_COUNTER]/[SPLIT_COUNTER]-[EPOCH_TIME].[FILE_EXTENSION]`

* `EPOCH_TIME`: Upload time as Unix time (seconds since 1970-01-01 UTC) in hex (e.g. `2020-01-01 00:00:00` becomes `5E0BE100`)

#### NOTE
Upload of many small log files has a higher network overhead and will result in lower throughput. Select a higher log file `split_size` (refer to the [logging configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/log.html.md#logging) section) for better throughput if the network stability allows it. For reliable networks, aim for at least 10 MB files.

#### NOTE
If the server-to-device confirmation that a log file has been uploaded successfully is lost (e.g. due to network problems), the device will upload the log file again. This can result in multiple identical log files with different `EPOCH_TIME` timestamps. Copies of the same log file (same `SESSION_COUNTER` and `SPLIT_COUNTER`) should be ignored or removed.

#### NOTE
If time-based splitting is used (`split_time_period` > 0), consider using the `split_time_offset` to avoid all devices uploading new log files to the server at the same time. For more information, refer to the [logging configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/log.html.md#logging) section.

### Metadata

S3 allows additional metadata to be attached to each file. The device adds the following S3 metadata:

* `X-Amz-Meta-Hw`: The device hardware version
* `X-Amz-Meta-Fw`: The device firmware version
* `X-Amz-Meta-Net`: The name of the network which was used to upload the file/object
* `X-Amz-Meta-Timestamp`: The *file-created* UTC timestamp of the file/object in format `YYYYMMDDTHHMMSSZ`
* `X-Amz-Meta-Put-Index`: S3 *PUT* operation counter

## Configuration over-the-air (COTA)

The device [configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/index.html.md#configuration) can be managed directly from the S3 server. Both the schema file and the configuration file are synchronized with the S3 server at the interval set in `s3.sync.ota` (see [S3 configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/s3/index.html.md#configuration-file-fields)).

### Schema file

The schema file is automatically uploaded once after each boot. This ensures that the server always knows the configuration rules of a specific device. If the firmware is updated, the device automatically uploads the schema file matching the new firmware.

The schema file is placed in the device root path and named as below:

`[BUCKET_NAME]/[DEVICE_ID]/schema-01.09.json`

### Configuration file

The device periodically checks the S3 bucket for updates to the configuration file. If the configuration file is updated on the server, it is automatically downloaded and applied by the device (the device reboots). If no configuration file is located on the server, it is automatically uploaded by the device.

The configuration file is placed in the device root path and named as below:

`[BUCKET_NAME]/[DEVICE_ID]/config-01.09.json`

#### WARNING
Configuration changes made via the SD-card will be overwritten if a configuration file is on the server. To apply local changes, first remove the server configuration file.

---

## Firmware over-the-air (FOTA)

The device checks the S3 bucket for firmware updates at the interval set in `s3.sync.ota`.

Updating firmware over-the-air works similarly to [updating firmware via the SD-card](https://canlogger.csselectronics.com/canedge-docs/ce2/firmware/index.html.md#update-from-sd-card). The firmware file is placed in the device S3 root path and named `firmware.bin`:

`[BUCKET_NAME]/[DEVICE_ID]/firmware.bin`

If a valid firmware file is added to this path, the device downloads and stores it on the SD-card. For a new `MAJOR` or `MINOR` version, a compatible configuration file is required (see [Configuration update](https://canlogger.csselectronics.com/canedge-docs/ce2/firmware/index.html.md#configuration-update)).

### Same MAJOR/MINOR version (e.g. 01.02.03 to 01.02.04)

1. The `firmware.bin` firmware file is placed in `[BUCKET_NAME]/[DEVICE_ID]/firmware.bin`
2. The device downloads the firmware file and reboots
3. The device continues to use the same configuration file

### New MAJOR/MINOR version (e.g. 01.02.03 to 01.03.00)

1. The new configuration file `config-01.03.json` is placed in `[BUCKET_NAME]/[DEVICE_ID]/config-01.03.json`
2. The `firmware.bin` firmware file is placed in `[BUCKET_NAME]/[DEVICE_ID]/firmware.bin`
3. The device downloads the firmware and configuration files and reboots
4. The device uses the updated configuration file

#### NOTE
If no compatible configuration file is found for a new `MAJOR` or `MINOR` version, the update is aborted.

The firmware file is deleted from the server once it has been downloaded, also if the update is aborted. This prevents the device from repeatedly downloading the firmware file, which could result in high data usage. After an aborted update, add the configuration file and upload the firmware file again.

## Server certificates over-the-air

The device checks S3 for server certificate updates at the interval set in `s3.sync.ota`.

Updating server certificates over-the-air works similarly to [Local installation of certificate(s)](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/s3/s3_security.html.md#local-installation-of-certificate-s). The server certificate bundle is placed in the S3 device root path and named `certs_server.p7b`:

`[BUCKET_NAME]/[DEVICE_ID]/certs_server.p7b`

If a valid server certificate bundle file is added to this path, the device downloads and stores it on the SD-card and reboots. Refer to [Prepare certificate(s)](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/s3/s3_security.html.md#prepare-certificate-s) on how to prepare a server certificate bundle.

#### WARNING
When updating the server certificate bundle over-the-air, special care must be taken to ensure that the device can access a server both before and after the update. It is recommended to always include both the *current* and *new* certificates in the bundle while any transition is performed.

Below are recommended server certificate bundle update sequences. Refer to [List of installed certificates](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/s3/s3_security.html.md#list-of-installed-certificates) for information on how to verify loaded certificates (used in the sequences below).

### Upgrade a server connection from HTTP to HTTPS (TLS)

1. Generate a server certificate bundle (`certs_server.p7b`) with the certificate(s)
2. Upload the server certificate bundle to the S3 server
3. Wait for the device file to show that the certificate has been loaded
4. Upload an updated configuration file to the S3 server with HTTPS enabled: Change the `endpoint` prefix from `http://` to `https://` and, if required, the `port` (e.g. `443`)

### Replace a soon-to-expire certificate

1. Generate a server certificate bundle (`certs_server.p7b`) with both certificates (the *soon-to-expire* and the *new* one)
2. Upload the server certificate bundle to the S3 server
3. Wait for the device file to show that both certificates have been loaded
4. Generate a server certificate bundle with only the *new* certificate
5. Upload the server certificate bundle to the S3 server
6. Wait for the device file to show that only the new certificate has been loaded

#### WARNING
The above sequence assumes that both certificates are valid during the process.

### Change to another S3 endpoint

1. Generate a server certificate bundle (`certs_server.p7b`) with the *current* and *new* certificate(s)
2. Upload the server certificate bundle to both the *current* and *new* S3 servers
3. Wait for the device file to show that both certificates have been loaded
4. Upload the new configuration file to the *current* server with the updated server information (pointing to the *new* server)
5. Wait for the device to connect to the *new* server (monitor whether either the configuration file or `device.json` is uploaded)
6. Generate a server certificate bundle (`certs_server.p7b`) with only the *new* certificate(s)
7. Upload the server certificate bundle to the *new* S3 server
8. Wait for the device file to show that only the new certificate(s) have been loaded

---
* <a id='fn-s3-bucket-share'>**[1]**</a> Multiple CANedge devices can share the same S3 bucket.

# TLS cipher support

The CANedge2 proposes the following ciphers for handshaking and encrypting the communication with the remote server.
The server must support at least one of the proposed ciphers. All ciphers require an RSA based server certificate.

| Cipher                                | Group 1   | Group 2   | Group 3   |
|---------------------------------------|-----------|-----------|-----------|
| TLS_RSA_WITH_AES_128_CBC_SHA          | X         | X         | X         |
| TLS_DHE_RSA_WITH_AES_128_CBC_SHA      | X         | X         | X         |
| TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA    | X         | X         | X         |
| TLS_RSA_WITH_AES_128_CBC_SHA256       |           | X         | X         |
| TLS_DHE_RSA_WITH_AES_128_CBC_SHA256   |           | X         | X         |
| TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA256 |           | X         | X         |
| TLS_RSA_WITH_AES_128_GCM_SHA256       |           |           | X         |
| TLS_DHE_RSA_WITH_AES_128_GCM_SHA256   |           |           | X         |
| TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 |           |           | X         |

#### NOTE
The ciphers are divided into 3 groups (1, 2, and 3). The device attempts connection with group 1 first, then 2, and finally 3.

## Configuration explained

*This section contains additional information and examples.*

---

### Permission

The `permission` setting controls the web server permission level:

- *Read only*: View and download files from the device.
- *Read, write and execute*: View, download, remove and upload files from/to the device (e.g. upload new configuration file).

#### NOTE
Upload is limited to the configuration file, the firmware file (`firmware.bin`) and the certificate bundle (`certs_server.p7b`).

---

### Security

The `security` setting controls the web server access control level:

- *None*: No access control.
- *Password* / *Password (encrypted)*: Password protection using HTTP Digest Access Authentication (see below). With *Password (encrypted)*, the password is stored in encrypted form in the configuration file (see [Security](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/general.html.md#security)).

Password protection uses HTTP *Digest Access Authentication* as described in [RFC 2617](https://datatracker.ietf.org/doc/html/rfc2617). Most browsers support digest authentication and automatically prompt for username and password.

The server supports a single user with the fixed username `user` (the associated password is set in the configuration file).

#### NOTE
*Digest Access Authentication* (MD5) provides limited security, and the connection is not encrypted (HTTP). Use the web server in trusted networks only.

---

### Web page

The web page allows the user to browse the filesystem and to download, upload and delete files<sup>[1](#fn-web-page-permission)</sup>. For information on how to find the web page, see the top of this page.

For a machine-friendly web server interface, see [Web server API](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/webserver/webserver_api.html.md#web-server-api).

| ![image](configuration/connect/protocols/webserver/webpage.png)   |
|-------------------------------------------------------------------|

#### WARNING
Web browsers often automatically add `https`. The web server does not currently support TLS. If the page does not load, make sure the address starts with `http://`.

#### WARNING
Web browsers may consider the `.MF4` log files as an unknown / insecure file type and initially try to block downloads.

### Configuration update

The device configuration file can be updated through the web server (when the `permission` setting allows *write*). The device reboots when a new configuration file is uploaded (if it is compatible with the running firmware).

### Certificate bundle update

The device certificate bundle file can be updated through the web server (when the `permission` setting allows *write*). The device reboots when a new certificate bundle file is uploaded.

---

### Firmware update

The device firmware can be updated through the web server (when the `permission` setting allows *write*).

#### Update to firmware with same MAJOR/MINOR version (example: 01.02.03 to 01.02.04)

1. Upload the new firmware file (`firmware.bin`)
2. The device applies the new firmware and reboots
3. The device loads the configuration file (`config-01.02.json`)

#### Update to firmware with new MAJOR/MINOR version (example: 01.02.03 to 01.03.00)

1. **First** upload the new configuration file (`config-01.03.json`)
2. **Then** upload the new firmware file (`firmware.bin`)<sup>[2](#fn-firmware-discarded)</sup>
3. The device applies the new firmware and reboots
4. The device deletes the old configuration file (`config-01.02.json`)
5. The device loads the configuration file (`config-01.03.json`)

# Web server API

> ##### On this page

The device exposes a REST API (endpoint `/api/`). The API can be used to programmatically interface with the device web server.

The device storage is navigated by adding the device path to the endpoint `/api/<DEVICE_STORAGE_PATH>`.

#### NOTE
The device only supports **one** concurrent connection, and automatically closes the socket after each request, regardless of whether the client wishes to keep the socket open (using HTTP headers). To avoid errors, it can be necessary to include small delays between API calls.

The Python module `canedge_http` provides helper functions making it easy to e.g. list, download and delete files through the API from Python. See [https://github.com/CSS-Electronics/canedge_http](https://github.com/CSS-Electronics/canedge_http) for more information.

In the following, the API is demonstrated using the *cURL* command-line tool. The examples assume that the device is assigned IP `192.168.1.100`. *cURL* supports digest authentication (if enabled in the device configuration) as demonstrated below:

```console
$ curl --user user:<password> --digest http://192.168.1.100/api/
```

The remaining examples assume that `security` is set to *None*. Add `--user user:<password> --digest` when password protection is enabled.

[Signal interpretation]:

# Signal interpretation

Several configuration sections use a similar structure for configuring a signal interpretation (decoding). Different conventions defining signal interpretation exist. The CANedge configuration adopts the convention used by  *.DBC* files.

The example below demonstrates how the interpretation of the signal *Epoch* from message *GnssTime* (ID 102 = `0x66`) defined in a  *.DBC* file is entered in the configuration file.

The  *.DBC* file section describing the *GnssTime* message (ID 102) is:

Section of a DBC file

```none
BO_ 102 GnssTime: 6 Vector__XXX
 SG_ TimeValid : 0|1@1+ (1,0) [0|1] "" Vector__XXX
 SG_ TimeConfirmed : 1|1@1+ (1,0) [0|1] "" Vector__XXX
 SG_ Epoch : 8|40@1+ (0.001,1577840400) [0|0] "s" Vector__XXX
```

The signal interpretation of the *Epoch* signal is defined by the final line. The line is explained below:

#### Fields of the *Epoch* signal definition

| DBC value          | Field             |
|--------------------|-------------------|
| Epoch              | Signal name       |
| 8                  | Bit position      |
| 40                 | Bit length        |
| 1                  | Byte order        |
| +                  | Type              |
| (0.001,1577840400) | Factor and offset |

*Bit position*, *bit length*, *factor* and *offset* can be copied directly into the configuration file. *Byte order* and *type* are defined by the following mappings:

#### *Byte order*

|   DBC value | Byte order   |
|-------------|--------------|
|           0 | Motorola     |
|           1 | Intel        |

#### *Type*

| DBC value   | Type     |
|-------------|----------|
| +           | Unsigned |
| -           | Signed   |

#### NOTE
Only unsigned signals are supported.

#### WARNING
GUI tools supporting the DBC file format may use a different convention for displaying e.g. bit position. It is recommended to use the information directly from the  *.DBC* file when configuring the CANedge.

# Filesystem

The SD-card filesystem is organized as illustrated in the example below<sup>[1](#fn-version)</sup>:

```text
/
├─ config-XX.YY.json
├─ schema-XX.YY.json
├─ uischema-XX.YY.json
├─ device.json
├─ meta
│  └── ...
└─ LOG
   └─ [DEVICE_ID]
      ├─ 00000001
      │  ├─ 00000001.MF4
      │  ├─ 00000002.MF4
      │  └─ ...
      ├─ 00000002
      │  ├─ 00000001.MF4
      │  ├─ 00000002.MF4
      │  └─ ...
      └─ ...
```

* `config-XX.YY.json`: [Configuration file](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/index.html.md#configuration) (device configuration)
* `schema-XX.YY.json`: [Schema file](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/index.html.md#configuration) (configuration rules)
* `uischema-XX.YY.json`: UI schema file (configuration presentation)
* `device.json`: [Device file](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/device-file.html.md#device-file) (device information)
* `LOG/`: Directory containing log files (see [Naming](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/log-file.html.md#naming) for more information)
* `meta/`: Temporary directory for setting the internally stored *session counter* (see [Setting session counter](#setting-session-counter) for more information)

#### NOTE
The default configuration file, schema file, UI schema file and device file are automatically re-created if deleted by the user.

## Replacing SD-card

The SD-card is **not** *locked* to the device. If the card is replaced (see [SD-card hardware requirements](https://canlogger.csselectronics.com/canedge-docs/ce2/hardware/sd-card.html.md#type)), be aware of the following points:

- If the card is replaced by a card from another CANedge, it is recommended to clear the card
- The configuration file can optionally be copied to the new card (otherwise a default configuration file is created automatically)

## Setting session counter

#### WARNING
The session counter is stored in battery-backed memory and is lost if the internal battery is removed or replaced. If the session counter is lost, the device continues from session 50000000. After replacing the battery, set the session counter to continue the session numbering of the existing log files.

To manually set the session counter, create the `meta` directory in the root of the SD-card. Inside the directory, create a file called `meta_log.json` with the following template:

```json
{
   "session": 123
}
```

Replace 123 with the session counter of the next session. To continue the numbering of the existing log files, use the highest session counter on the SD-card plus one (see [Naming](https://canlogger.csselectronics.com/canedge-docs/ce2/filesystem/log-file.html.md#naming)).

When the device boots, it reads `meta/meta_log.json`, stores the session counter internally and deletes the file.

## Fields explained

* `id`: Device unique ID (also used as the `[DEVICE_ID]` log file directory name)
* `type`: Device type (CANedge2 = 0000001F)
* `kpub`: Device public key in base64 format
* `fw_ver`: Firmware version
* `hw_ver`: Hardware version of the main board, followed by the hardware version of the extension board (`[main]/[extension]`)
* `cfg_ver`: Configuration file version
* `cfg_name`: Configuration file name
* `cfg_crc32`: Configuration file checksum
* `sch_name`: Schema file name
* `log_meta`: Device metadata string from the configuration (`general.device.meta`)
* `space_used_mb`: Used and total SD-card space in MB (`[used]/[total]`)
* `sd_info`: Information about the SD-card, including unique serial number in hex
* `sd_used_lifespan`: The SD-card self-reported health in percent of lifetime used, or `?` if unavailable
* `reset_cause`: For debugging purposes

## Format

The CANedge logs data in the industry-standard MDF4 format, standardized by *ASAM*. MDF4 is a binary format which allows compact storage of large amounts of measurement data. It is specifically designed for bus frame logging across e.g. CAN bus, LIN bus and Ethernet. MDF4 is widely adopted by the industry and supported by many existing tools.

Specifically, the CANedge uses MDF version 4.11 (file extension: `.MF4`).

### Timestamps

Each record is timestamped with 50 µs resolution<sup>[2](#fn-rtcchanges)</sup>.

### Finalization & sorting

The CANedge stores log files as *unfinalized* and *unsorted* to enable power safety. Finalization<sup>[3](#fn-finalization)</sup> and sorting<sup>[4](#fn-sorting)</sup> can be done as a post-processing step to speed up work with the files.

#### NOTE
It may be necessary to finalize/sort a log file before it is loaded into some MDF tools.

Additional metadata about the device is stored in the files, including many of the fields in the device file:

* `serial number`: Device unique ID number
* `device type`: Device type (CANedge2 = 0000001F)
* `firmware version`: Firmware version
* `hardware version`: Hardware version
* `config crc32 checksum`: Configuration file checksum
* `storage total`: The SD-card total space in kB
* `storage free`: The SD-card free space in kB
* `storage id`: The SD-card identifier
* `session`: File session counter
* `split`: File split counter
* `comment`: Device metadata string from the configuration (`general.device.meta`)

---

## Naming

Log files are organized by the following path structure:

`LOG/[DEVICE_ID]/[SESSION_COUNTER]/[SPLIT_COUNTER].[FILE_EXTENSION]`

The path is constructed from the following parts:

* `LOG`: Static directory name used to store log files
* `DEVICE_ID`: Globally unique device ID
* `SESSION_COUNTER`: Increased by one each time the device boots<sup>[1](#fn-session-counter)</sup>
* `SPLIT_COUNTER`: Reset to 1 each time the device boots and increased by one for each file split
* `FILE_EXTENSION`: `MF4`, `MFC`, `MFE` or `MFM`, depending on compression and encryption (see [File extension](#file-extension))

For details on log file splits and related limits, see the [logging configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/log.html.md#logging) section.

### File extension

The default extension is `.MF4`. With compression/encryption enabled the extension changes:

| Compression enabled   | Encryption enabled   | File extension   |
|-----------------------|----------------------|------------------|
|                       |                      | `.MF4`           |
| X                     |                      | `.MFC`           |
|                       | X                    | `.MFE`           |
| X                     | X                    | `.MFM`           |

For details on compression and encryption, see the [logging configuration](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/log.html.md#logging) section.

### Path example

Example: Log file path: `LOG/3B912722/00000004/00000189.MF4`

* `LOG`: The static directory common for all log files
* `3B912722`: The unique ID of the device which generated the log file
* `00000004`: Generated during session 4
* `00000189`: Is log file number 189 of the session
* `MF4`: File type

---

## Generic header

Plain MDF4 files use the extension `.MF4`. Encrypted and/or compressed files use a custom header to identify and store relevant information for the files. All file headers consist of a generic 20-byte header, followed by any specialized fields.

The generic header starts with an identifying sequence of the ASCII code for `Generic File`<sup>[5](#fn-magic)</sup>. This is followed by the header version (`V Ge`, currently `0x01`), file type version (`V FT`), file type (`FT`) and file sub-type (`FTI`). Finally, the device ID is stored. All numbers stored in the generic header are unsigned and big-endian formatted.

```none
| <-                     8 bytes                       -> |
|  Byte | Byte | Byte | Byte | Byte | Byte | Byte | Byte  |
|   'G'    'e'    'n'    'e'    'r'    'i'    'c'   ' '-> |
| <-'F'    'i'    'l'    'e' | V Ge | V FT |  FT  |  FTI  |
|    Device ID (Uint32, BE)  |
```

If required, a generic file may contain a footer as well, as specified by the format.

### Encrypted files

Encrypted files have a file type of `0x11`. The device supports AES encryption in Galois Counter Mode (GCM), with a file sub-type of `0x01`. The current version of the format is `0x00`. The encrypted file header stores three additional fields:

* The 12-byte initialization vector
* The number of hashing iterations for the key, stored as a 32-bit unsigned number in big-endian format
* 16 bytes of salt data for the hashing of the key

```none
| <-                    8 bytes                      -> |
| Byte | Byte | Byte | Byte | Byte | Byte | Byte | Byte |
|                       IV/Nonce                     -> |
| <-       IV/Nonce         |  Iterations (Uint32, BE)  |
|                         Salt                       -> |
| <-                      Salt                          |
```

The encrypted file contains an additional footer. This stores the 16-byte tag generated when AES runs in GCM mode. When decrypting, this tag should be checked to ensure the validity of the decrypted data. There is no alignment requirement for the footer.

```none
| <-                    8 bytes                      -> |
| Byte | Byte | Byte | Byte | Byte | Byte | Byte | Byte |
|                        GCM Tag                     -> |
| <-                     GCM Tag                        |
```

### Compressed files

Compressed files have a file type of `0x22`. At present, the only supported compression format is heatshrink-based. This is denoted by a file sub-type of `0x01`. The current version of the format is `0x01`. The additional header data are two unsigned 32-bit numbers: The lookahead size as a base-2 exponent (e.g. 4 = 2^4 = 16 bytes) and the window size in bytes.

```none
| <-                    8 bytes                      -> |
| Byte | Byte | Byte | Byte | Byte | Byte | Byte | Byte |
|   Lookahead (Uint32, BE)  |    Window (Uint32, BE)    |
```

Following the header is the compressed data stream. Following the data stream is a footer with a checksum over the compressed data. There is no alignment requirement for the footer. The checksum format is often found online as CRC32 JAM or JAMCRC.

```none
| <-      4 bytes        -> |
| Byte | Byte | Byte | Byte |
|     CRC32 (Uint32, BE)    |
```

### Encrypted and compressed files

If the file is both encrypted and compressed, it has been processed in two steps/streams. First the data is piped through a compression step, next it is piped through an encryption step. Each step can have its own version.

---
* <a id='fn-session-counter'>**[1]**</a> The session counter is also increased by one if the counter of splits in one session exceeds 256.
* <a id='fn-rtcchanges'>**[2]**</a> Changes to the system time (RTC) caused by time synchronization (see [Real-time clock](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/rtc/index.html.md#real-time-clock)) take effect on the next file split, or when the device boots.
* <a id='fn-finalization'>**[3]**</a> The MDF4 file header includes information on how to finalize the MDF4 file before use.
* <a id='fn-sorting'>**[4]**</a> Sorting refers to an organization of the log records, which enables fast indexing. It is not related to sorting of timestamps.
* <a id='fn-magic'>**[5]**</a> `Generic File` maps to 12 bytes of ASCII, with no zero termination of the string.

## Firmware versioning & naming

The device firmware versioning is inspired by the semantic versioning system.

Each firmware version consists of three two-digit numbers: `MAJOR`, `MINOR`, `PATCH`:

* `MAJOR`: Incompatible changes to the configuration. Existing parts of the schema are changed (e.g. restructured), so an existing configuration must be adapted.
* `MINOR`: Additions to the configuration (e.g. new options or new fields). Existing parts of the schema are unchanged, so an existing configuration remains valid, but new fields may need to be added and set.
* `PATCH`: Changes that do not affect the configuration (e.g. bug fixes or performance improvements).

The firmware is distributed as a *firmware package* (zip) named as follows:

`firmware-[MAJOR].[MINOR].[PATCH].zip`

Example:

`firmware-01.02.03.zip`

The firmware package contains:

* `firmware.bin`: The *firmware file*, used to update the device
* `config-XX.YY.json`: The default configuration file
* `schema-XX.YY.json`: The schema file
* `uischema-XX.YY.json`: The UI schema file

---

## Firmware update

The device supports in-the-field firmware updates.

#### NOTE
The firmware update process is power safe (tolerates power failures). However, it is recommended to ensure that the process completes.

### Update process

The firmware update process begins when the device is powered and has been prepared with a new firmware file:

1. Power is applied to the device
2. The green *Power* (PWR) LED comes on (later than usual, can take a few seconds)
3. If the firmware file is valid, the green PWR LED blinks 5 times. Otherwise, the update is skipped and the existing firmware starts
4. The green PWR LED remains solid while the firmware is updated (~30 s)
5. If the update is successful, the green PWR LED blinks 5 times, otherwise the red *Memory* (MEM) LED blinks 5 times
6. The updated firmware is started and the device is ready for logging
7. If the firmware of any integrated modules needs to be updated, then these updates are applied now (see [Update of module firmware](#update-of-module-firmware))

#### WARNING
The firmware file should never be manually deleted during the update process. The device automatically removes the firmware file when the update has completed.

#### Update of module firmware

The integrated modules run their own firmware ([module firmware](https://canlogger.csselectronics.com/canedge-docs/ce2/glossary.html.md#term-Module-firmware)). The module firmware is updated while the device is (partly) operational.
If power is lost during the update of the module firmware, the update resumes the next time the device boots.

### Configuration update

If a device is updated to a firmware version with a different `MAJOR` or `MINOR` number, a new compatible configuration file is required, named as described in [Naming](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/index.html.md#naming). A default configuration file and corresponding schema file are contained in the firmware package.

To modify an existing configuration file, it can be useful to load the new schema file in an editor together with the old configuration file. After making the necessary updates, save the modified configuration file with a name matching the new version.

#### NOTE
When updating from the SD-card, the firmware can be updated without providing a new compatible configuration file. In this case, the device deletes the old configuration file and creates a default configuration file on the SD-card.

When updating over-the-air, an updated and compatible configuration file is required. If it is not available, the update is aborted. This ensures that the device keeps its network connection.

### Update from SD-card

The firmware can be updated by placing a firmware file on the SD-card and powering the device:

1. Download the firmware package (see [Download firmware](https://canlogger.csselectronics.com/canedge-docs/ce2/firmware/download.html.md#download-firmware))
2. Place the `firmware.bin` file on the SD-card (root directory)
3. If `MAJOR`/`MINOR` is different, place a compatible configuration file on the SD-card (if none is provided, the device creates a default configuration file during the update)
4. Power on the device and wait for the update process to complete

#### NOTE
An incompatible firmware file does not break the device.

#### Same MAJOR/MINOR version (e.g. 01.02.03 to 01.02.04)

1. Download `firmware-01.02.04.zip` and unzip it
2. Copy `firmware.bin` to the SD-card
3. Keep the configuration file (`MAJOR` and `MINOR` are unchanged)
4. Power on the device and wait for the update process to complete

#### New MAJOR/MINOR version (e.g. 01.02.03 to 01.03.00)

1. Download `firmware-01.03.00.zip` and unzip it
2. Copy `firmware.bin` to the SD-card
3. Place a compatible configuration file (`config-01.03.json`) on the SD-card (otherwise, a default configuration file is created during the update)
4. Power on the device and wait for the update process to complete

### Update over-the-air

The device firmware can be updated remotely:

* Through the S3 interface. See [Firmware over-the-air (FOTA)](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/s3/s3_management.html.md#firmware-over-the-air-fota).
* Through the web server. See [Firmware update](https://canlogger.csselectronics.com/canedge-docs/ce2/configuration/connect/protocols/webserver/index.html.md#firmware-update).

# Change Log
All notable changes to CANedge firmware will be documented in this file.

Types of changes:
- "Added": New features
- "Changed": Changes to existing functionality
- "Deprecated": Soon-to-be removed features
- "Removed": Removed features
- "Fixed": Bug fixes
- "Known issues": Known issues
- "Warning": Warnings

Abbreviations:
- CANedge1:      CE1
- CANedge1-GNSS: CE1G
- CANedge2:      CE2
- CANedge2-GNSS: CE2G
- CANedge3-GNSS: CE3G

## [Unreleased]

### Warning
- CE3G: Servers using ECDSA based TLS certificates are no longer supported

### Changed
- CE3G: TLS cipher suites aligned with CE2 and CE2G
- CE1, CE1G, CE2, CE2G, CE3G: MDF file header layout changed. The blocks of each channel group (acquisition name, CG and CN) are now stored together, the LIN channels use their own bus channel conversion blocks and the XML comments end with a newline. The header grows from 106800 to 106992 bytes. Channel groups, channels, record IDs, conversions and the logged data are unchanged, so MDF readers are not affected

### Fixed
- CE1, CE1G, CE2, CE2G, CE3G: Some LIN error frames were not logged correctly
- CE3G: Fixed issue where network time sync did not work on some devices
- CE2, CE2G: Schema rejected encrypted WiFi and web server passwords longer than 32 characters
